# Мастер-промпт: интерактивные карманные часы с управляемой 3D-разборкой

> Это готовое задание для AI-агента с доступом к рабочей папке, терминалу, браузеру и MCP. Передай ему этот файл целиком. Он должен самостоятельно подготовить окружение, установить недостающие навыки, подключить Blender MCP, создать 3D-модель и реализовать сайт.

## 1. Твоя роль и конечный результат

Ты — ведущий frontend-разработчик, технический 3D-художник, motion-дизайнер и специалист по WebGL. Создай законченный адаптивный сайт, центральным элементом которого будет настоящая интерактивная 3D-модель механических карманных часов.

Главная функция: пользователь двигает ползунок, и часы постепенно разбираются на отдельные детали. При движении ползунка назад те же детали точно возвращаются на свои места. Это управляемая пользователем объёмная exploded-view-анимация с непрерывным прогрессом.

Результат должен восприниматься как небольшая цифровая музейная экспозиция о часовом механизме: красивая предметная подача, понятное управление, убедительные материалы, видимая конструкция и аккуратная техническая логика.

Нужен работающий проект с исходниками и настоящей 3D-сценой. Выполни реализацию, проверь её в браузере и передай готовые файлы. Одного описания концепции, плана, макета или списка рекомендаций недостаточно.

Основной язык интерфейса, документации и отчётов — русский. Идентификаторы в коде и названия технических файлов могут быть английскими.

## 4. Самостоятельное подключение Blender MCP

### 4.1. Требуемый результат

Ты должен получить рабочую цепочку:

~~~text
AI-клиент
    → MCP-сервер Blender
        → локальное соединение с аддоном Blender
            → запущенная сцена Blender
                → создание и экспорт модели
~~~

Установка Python-пакета без работающего Blender не завершает этот этап. Установка аддона без доступных в AI-клиенте MCP-инструментов тоже не завершает этот этап.

### 4.2. Проверка окружения

Самостоятельно определи:

- операционную систему и доступные способы установки;
- используемый AI-клиент и поддерживаемый формат MCP-конфигурации;
- наличие Blender и его исполняемый файл;
- доступные Python, uv или другой предусмотренный выбранным сервером способ запуска;
- уже настроенные Blender MCP-подключения;
- местоположение пользовательского или проектного MCP-конфига;
- возможность перезагрузки MCP-сервера и обнаружения инструментов без потери текущей работы;
- доступность управления интерфейсом Blender или его Python API.

Не добавляй второй сервер с тем же назначением, если рабочий уже подключён.

### 4.3. Выбор реализации и установка

В качестве основного кандидата рассмотри проект:

[MCP for Blender — ahujasid/mcp-for-blender](https://github.com/ahujasid/mcp-for-blender).

Старый адрес ahujasid/blender-mcp может перенаправлять в этот репозиторий. На момент дополнения промпта, 29 октября 2026 года, README рекомендует новым установкам пакет mcp-for-blender.

Это сторонняя реализация интеграции, а не основание называть её официальным продуктом Blender Foundation.

Перед установкой прочитай актуальный README выбранного проекта. Проверь поддерживаемую версию Blender, необходимые зависимости, способ установки аддона, способ запуска сервера и доступные параметры соединения.

Выполни установку сам, используя поддерживаемый источник. Не копируй вслепую команды из памяти и не предполагай, что старый пример конфигурации подходит текущему клиенту.

Если установлен uv, основной документированный путь автоматической настройки:

~~~bash
uvx mcp-for-blender setup
~~~

Для отдельной установки аддона в документации предусмотрено:

~~~bash
uvx mcp-for-blender install-addon
~~~

По [README проекта](https://github.com/ahujasid/mcp-for-blender#quickstart) автоматический setup настраивает выбранные совместимые клиенты и устанавливает и включает аддон. Старое имя blender-mcp сохраняется для совместимости существующих установок. Перед выполнением ещё раз проверь документацию выбранной версии.

Интерактивные шаги установщика проходи самостоятельно доступными средствами. Если есть документированный неинтерактивный режим, используй его; не придумывай флаги. Перезапуск клиента планируй с сохранением состояния задачи.

Не переноси JSON-конфигурацию одного AI-клиента в TOML-конфигурацию другого. Определи настоящий формат и область действия настроек. Если доступна проектная конфигурация, предпочти её для относящихся к проекту параметров.

При отсутствии Blender самостоятельно установи доступную совместимую версию штатным способом. При отсутствии необходимых прав используй поддерживаемую пользовательскую или переносимую установку, если она подходит среде.

Установи и включи совместимый аддон Blender. Если это можно сделать через документированный Python API или разрешённую автоматизацию интерфейса, выполни это сам. Не заставляй пользователя нажимать кнопки, которые способен нажать или заменить командой сам.

### 4.4. Настройка соединения

1. Сохрани резервную копию изменяемой конфигурации.
2. Добавь сервер с уникальным понятным именем.
3. Укажи реальные пути к исполняемым файлам, если окружение клиента не наследует PATH терминала.
4. Согласуй адрес и порт MCP-сервера и аддона согласно документации выбранной версии.
5. Для локальной работы используй loopback-интерфейс; не открывай Blender во внешнюю сеть.
6. Запусти Blender с аддоном и включённым приёмом команд.
7. Перезапусти или обнови MCP-подключение поддерживаемым способом.
8. Проверь обнаружение инструментов в клиенте.

При stdio-транспорте сервер обычно запускается самим MCP-клиентом. Не поднимай второй конкурирующий процесс без необходимости. При другой архитектуре следуй документации реализации.

Blender MCP нужен на этапе разработки. Сайт для посетителя должен работать в обычном браузере без запущенного Blender, Python, MCP-сервера или доступа к локальному порту.

### 4.5. Обязательная проверка

Через реально подключённый MCP:

1. Получи информацию о текущей сцене.
2. Создай отдельную тестовую коллекцию с уникальным именем.
3. Добавь в неё небольшой тестовый объект.
4. Измени его положение или материал.
5. Повторно прочитай сцену и проверь, что изменение произошло.
6. Получи доступный снимок сцены или иное проверяемое подтверждение.
7. Удали только созданные тобой тестовые сущности.

После проверки переходи к моделированию часов.

Зафиксируй в SETUP_REPORT.md:

- реализацию и источник Blender MCP;
- версии Blender, сервера и аддона, если они определяются;
- фактическое расположение конфигурации без секретов;
- используемый транспорт и локальные параметры соединения;
- результаты чтения и изменения сцены;
- результат обнаружения инструментов;
- оставшиеся ограничения, если они есть.

Если MCP объективно нельзя подключить в текущей среде, не называй его подключённым и не перекладывай установку на пользователя. Сохрани выполненную настройку и точную причину ограничения. Продолжай создание модели через доступный Blender CLI/Python или процедурную 3D-геометрию. Рабочий сайт всё равно должен быть создан; резервный путь не даёт права скрыть незавершённое подключение.

## 5. Концепция сайта

Рабочее название проекта — «Ход времени».

Основная идея: посетитель рассматривает карманные часы как инженерный объект и буквально раскрывает их устройство одним движением.

Дизайн должен строиться вокруг часов, их материалов и движения деталей. Главная ценность первого экрана — сама управляемая 3D-модель.

Образ:

- музейная предметная съёмка;
- мастерская часовщика;
- точные концентрические формы;
- сталь, латунь, эмаль и стекло;
- спокойное направленное освещение;
- сдержанная типографика;
- ощущение веса и аккуратности механики.

Не превращай проект в интернет-магазин или типовой лендинг. Здесь не нужны цены, тарифы, фальшивые отзывы, логотипы партнёров, формы заявки и бессодержательные карточки преимуществ.

Главный визуальный акцент — живой трёхмерный объект. Второй — ползунок. Всё остальное помогает понять и исследовать механизм.

## 6. Визуальная система

### 6.1. Цвета

Возьми за основу такую палитру и уточни её после проверки контраста:

| Роль | Цвет | Применение |
| --- | --- | --- |
| Глубокий синий графит | #0E1620 | Основной фон |
| Сине-стальная поверхность | #16212E | Компактные панели управления |
| Светлая эмаль | #F1EEE7 | Основной текст |
| Холодное серебро | #B4BDCA | Второстепенный текст |
| Матовая латунь | #C49B5C | Активное состояние ползунка, выделение |
| Стальная линия | #334456 | Разделители и границы |

Оттенки материалов 3D-модели могут выходить за эту палитру: рубиновые камни, полированная сталь, тёплая латунь, синёные стрелки.

Следи, чтобы металлические блики не делали светлые детали неразличимыми. Избегай кислотных акцентов, декоративного неона и тяжёлых разноцветных градиентов.

Для обычного текста обеспечь контраст не ниже 4.5:1. Для крупных надписей и значимых графических элементов проверь соответствующие требования доступности. Не полагайся только на цвет при обозначении состояния.

### 6.2. Типографика

Выбери две совместимые гарнитуры с полноценной кириллицей:

- выразительную, но читаемую антикву для крупного заголовка; например, Cormorant Garamond;
- спокойный интерфейсный шрифт для управления и пояснений; например, Manrope.

Проверь наличие кириллицы в конкретных используемых файлах. Предпочти локальные WOFF2 и системные fallback-шрифты. Сайт не должен терять подписи из-за недоступного внешнего сервиса шрифтов.

Ориентировочный масштаб:

- главный заголовок на desktop: 64–88 px;
- главный заголовок на телефоне: 34–46 px;
- основной текст: 16–18 px;
- подписи элементов: 13–15 px;
- вспомогательные подписи: не мельче 12 px.

Используй fluid-размеры там, где это помогает адаптивности. Для процентов включи табличные цифры. Не оформляй весь интерфейс прописными буквами.

### 6.3. Поверхности и декоративные элементы

Панели управления должны быть компактными, с умеренным радиусом, тонкой границей и достаточным внутренним отступом.

Допустимы лёгкий световой ореол за моделью и едва заметные технические окружности, если они помогают композиции. Они не должны конкурировать с механизмом.

Не раскладывай весь контент по одинаковым округлым карточкам. Не добавляй декоративный стеклянный blur к каждому элементу.

- «Устройство» — открывает или прокручивает к объяснению деталей;
- «О проекте» — ведёт к короткому описанию демонстрации.

Не создавай навигацию по несуществующим разделам. Если контента мало, достаточно названия проекта и одной ссылки.

### 7.2. Основной экран

Пример основного текста:

**Заголовок:** «Время раскрывается.»

**Описание:** «Разберите карманные часы одним движением и рассмотрите, как устроен механизм.»

**Подсказка:** «Двигайте ползунок для разборки. Перетаскивайте часы, чтобы повернуть модель.»

На desktop расположи краткое вступление слева, а крупную сцену — по центру и справа. Объект должен занимать большую часть доступного пространства.

На телефоне используй вертикальный порядок: название и короткое вступление, сцена, ползунок, действия и сведения о выбранной детали.

### 7.3. Блок управления

Обязательные элементы:

- видимая подпись «Разборка часов»;
- процент прогресса;
- ползунок от 0 до 100%;
- подпись начального состояния «Собраны»;
- подпись конечного состояния «Разобраны»;
- действие «Собрать»;
- действие «Разобрать»;
- действие «Сбросить вид»;
- переключатель «Подписи деталей».

Когда запущена программная разборка или сборка, предоставь возможность остановить движение. Не показывай одновременно множество конкурирующих кнопок.

Промежуточные отметки 25%, 50% и 75% могут быть доступными кнопками перехода. Если это лишь декоративные деления, не оформляй их как интерактивные элементы.

### 7.4. Информация о детали

При выборе детали показывай небольшую панель:

- название;
- краткое объяснение функции;
- материал, если он действительно определён;
- действие снятия выделения.

Примеры:

- «Циферблат. Показывает время и закрывает механизм со стороны стрелок.»
- «Заводной барабан. Содержит пружину, запасённая энергия которой приводит механизм в движение.»
- «Колёсная передача. Передаёт вращение между узлами механизма.»
- «Баланс. Колебательный узел, участвующий в регулировании хода часов.»
- «Задняя крышка. Защищает механизм со стороны корпуса.»

Не выдумывай историческое происхождение, производителя, точность хода или число камней реальной модели.

### 7.5. Короткое пояснение ниже сцены

Добавь небольшой раздел «Что скрыто внутри» с понятным описанием принципа: пружина запасает энергию, передача распределяет движение, спуск и баланс регулируют его, стрелки показывают время.

Эта демонстрационная модель не является инструкцией по ремонту конкретного исторического механизма. Скажи об этом одной спокойной фразой в описании проекта, если конструкция условная.

## 8. Требования к 3D-модели

### 8.1. Тип часов

Создай классические механические карманные часы с открытым циферблатом:

- круглый металлический корпус;
- заводная головка сверху;
- дужка для цепочки;
- светлый эмалевый циферблат;
- часовые метки;
- две основные стрелки;
- небольшая секундная индикация, если она качественно реализована;
- прозрачное защитное стекло;
- видимый при разборке механизм;
- отдельная задняя крышка.

Выбери один связный дизайн. Не смешивай случайно карманные часы, наручный хронограф, современный смарт-дисплей и фантастический реактор.

Модель может быть авторской, вдохновлённой классическими карманными часами, без логотипов существующих брендов.

### 8.2. Уровень детализации

В собранном виде силуэт должен сразу считываться как карманные часы. В разобранном виде должны быть видны конструктивные слои.

Целевой объём — примерно 30–60 осмысленных объектов или групп, в том числе не менее 24 отдельно различимых деталей. Несколько мелких креплений можно объединить в логические наборы.

Нужны:

| Узел | Визуальная роль | Поведение при разборке |
| --- | --- | --- |
| Ободок | Передний металлический контур | Отходит вперёд |
| Стекло | Прозрачная линза над циферблатом | Отделяется отдельным слоем |
| Часовая стрелка | Короткая фигурная стрелка | Отходит от оси |
| Минутная стрелка | Более длинная стрелка | Отходит от оси отдельной деталью |
| Секундный узел | Дополнительная индикация | Разбирается, если предусмотрен |
| Циферблат | Эмалевый диск с метками | Отходит вперёд |
| Опора циферблата | Связь циферблата и механизма | Отделяется от основного блока |
| Мосты | Фиксация и оформление узлов | Открывают внутреннюю передачу |
| Основная платина | Несущая основа механизма | Остаётся главным ориентиром |
| Несколько зубчатых колёс | Передача движения | Разносятся с небольшими радиальными смещениями |
| Заводной барабан | Источник энергии | Отделяется от передачи |
| Баланс и его мост | Регулирующий узел | Отходят согласованной группой |
| Заводная головка и вал | Завод и установка времени | Сохраняют понятную связь с корпусом |
| Дужка | Характерный верхний элемент | Остаётся связанной с корпусом |
| Корпус | Основной несущий контур | Сохраняет читаемость сборки |
| Задняя крышка | Защитный задний слой | Отходит назад |
| Винты и втулки | Детали сборки | Разводятся в конце анимации |

Реализуй настоящие зубья хотя бы у хорошо видимых колёс. Не заменяй весь механизм одинаковыми цилиндрами.

Циферблат должен иметь читаемые цифры или метки и аккуратные стрелки. Круглая металлическая коробка без циферблата не удовлетворяет заданию.

### 8.3. Материалы

Используй физически правдоподобные материалы:

- корпус: состаренная или сатинированная латунь;
- отдельные детали: полированная сталь;
- мосты: латунь с умеренной шероховатостью;
- циферблат: светлая эмаль;
- стрелки: тёмная или синёная сталь;
- стекло: прозрачный материал с контролируемыми отражениями;
- декоративные камни: небольшие тёмно-красные акценты.

Не делай все металлические детали идеально зеркальными. Разделяй материалы по roughness, направлению обработки и силе отражения.

Избегай чрезмерной грязи, гигантских царапин и одинакового шумового bump на всех поверхностях. Микрофактура должна соответствовать масштабу предмета.

Точные значения материалов подбери по результату в целевом браузерном рендерере, а не только по красивому рендеру Blender.

### 8.4. Что допускается упростить

Можно упростить невидимые резьбы, мелкие фаски и форму отдельных внутренних деталей. Допустима демонстрационная компоновка механизма, если она визуально связная.

Не обещай инженерную точность, если модель не построена по проверенной документации. Важнее убедительная конструкция, согласованная анимация и объяснимость узлов.

## 9. Моделирование через Blender MCP

После проверки подключения создай модель через Blender. Для повторяемых операций используй Python-скрипты, запускаемые через поддерживаемый инструмент MCP или Blender.

Рекомендуемая последовательность:

1. Создай отдельную сцену или коллекцию проекта, не удаляя пользовательские объекты.
2. Построй базовый корпус, циферблат и заводную головку.
3. Проверь масштаб, силуэт и положение осей.
4. Создай стрелки, стекло и крышки.
5. Построй основную платину, мосты, колёса и барабан.
6. Добавь баланс, крепления и характерные мелкие элементы.
7. Назначь материалы и имена.
8. Проверь собранное состояние.
9. Подготовь метаданные разборки.
10. Экспортируй модель и проверь её в браузере.

Сохрани:

- редактируемую модель .blend;
- скрипт создания или воспроизводимой подготовки модели;
- скрипт экспорта;
- итоговую .glb;
- JSON-манифест деталей;
- сведения об используемых материалах и внешних ресурсах.

Работай идемпотентно: повторный запуск скрипта не должен удваивать модель. Управляй только собственной коллекцией и собственными файлами проекта.

Не используй глобальное удаление всей сцены, если в ней есть чужая работа. При сохранении поверх существующего файла сначала убедись, что он относится к этому проекту, и сохрани восстанавливаемую копию при необходимости.

### 9.2. Экспорт

Экспортируй glTF Binary с сохранением необходимых отдельных узлов.

Не объединяй все часы в один mesh: это уничтожит возможность разборки деталей.

Проверь:

- единый понятный масштаб;
- корректные нормали;
- координаты после преобразования осей Blender → glTF;
- положение центра модели;
- стабильные имена;
- отсутствие лишних камер, источников света и тестовых объектов;
- поддержку материалов целевым рендерером;
- отсутствие потерянных текстур;
- отсутствие отрицательных масштабов и неожиданного наследования трансформаций.

Текст, процедурные шейдеры и специфические материалы Blender не всегда переносятся в glTF как выглядят в Blender. Конвертируй, запекай или воспроизводи их в браузере там, где это требуется.

Сложное стекло можно настроить на стороне Three.js после загрузки модели. Проверь его именно в финальной сцене.

## 10. Система координат и данные разборки

### 10.1. Координаты

В пространстве анимации договорись:

- центр часов находится около начала координат;
- ось Y направлена вверх, к заводной головке;
- положительная Z направлена вперёд, от циферблата к зрителю;
- отрицательная Z направлена к задней крышке;
- диаметр корпуса служит основной единицей композиции.

Например, нормализуй диаметр примерно до 2.6 условных единиц. Это ориентир, а не обязательный физический размер.

Проверь, что экспортированная модель действительно соответствует этой системе. Не подставляй координаты Blender напрямую в браузер, не проверив преобразование осей.

### 10.2. Отдельные анимационные контейнеры

По возможности помести каждую независимо движущуюся деталь в собственный carrier/group под общим родителем.

Геометрия внутри carrier сохраняет собственные локальные трансформации. Анимация управляет контейнером.

Не анимируй одновременно родителя и вложенный узел одинаковым смещением: это даст удвоенное движение. Если узел содержит сборку из нескольких неподвижных относительно друг друга деталей, двигай общую группу.

Все rest-transform и exploded-transform должны быть выражены в согласованном локальном пространстве.

### 10.3. Манифест

Опиши каждую анимируемую деталь данными, а не набором разрозненных условий.

Предусмотри поля:

~~~ts
type Vec3 = [number, number, number];
type Quat = [number, number, number, number];

type WatchPart = {
  id: string;
  nodeName: string;
  title: string;
  description: string;
  materialLabel?: string;
  category: "case" | "dial" | "movement" | "fastener";
  start: number;
  end: number;
  restPosition: Vec3;
  explodedOffset: Vec3;
  restQuaternion: Quat;
  explodedQuaternion: Quat;
  restScale: Vec3;
  labelAnchor: Vec3;
  selectable: boolean;
};
~~~

Это рекомендуемый контракт. При необходимости добавь данные для промежуточных точек траектории и отдельного вращения винтов. Не добавляй поля, которые нигде не используются.

Выбери один источник истины для исходных трансформаций: проверенный экспортный манифест или однократное считывание модели при инициализации. Не сохраняй расходящиеся версии в нескольких местах.

## 11. Главная механика ползунка

### 11.1. Единый прогресс

Единственная логическая величина разборки — progress в диапазоне от 0 до 1.

- 0 — часы полностью собраны.
- 0.25 — внешний корпус начинает раскрываться.
- 0.5 — циферблат и передние слои отделены, механизм становится видимым.
- 0.75 — основные внутренние узлы разведены.
- 1 — все предусмотренные детали находятся в финальном разобранном положении.

Точные промежуточные композиции подбери так, чтобы они были красивыми и понятными.

Видимый ползунок работает в диапазоне 0–100 с достаточно мелким шагом, например 0.1. Его значение преобразуется в нормализованный progress.

Не делай пять заранее отрендеренных картинок вместо непрерывной разборки. Каждое промежуточное значение должно задавать реальную конфигурацию 3D-сцены.

### 11.2. Прямая зависимость от положения

Положение ползунка задаёт состояние сцены напрямую. Если остановить ползунок, детали должны остановиться в соответствующей конфигурации.

Не запускай отдельную независимую анимацию по каждому событию input. Не накапливай очереди tween-анимаций при быстрых движениях.

Во время ручного перемещения приоритет у пользователя. Программный автопоказ немедленно прекращается.

Дополнительное сглаживание, если оно вообще нужно, не должно создавать заметное отставание от ползунка. По умолчанию предпочти прямую связь без временного хвоста.

### 11.3. Абсолютные трансформации

Для каждой детали вычисляй результат от её исходного состояния, а не от прошлого кадра.

Рекомендуемая схема:

~~~text
u = clamp((progress - start) / (end - start), 0, 1)
e = u × u × (3 - 2 × u)

position = restPosition + explodedOffset × e
quaternion = slerp(restQuaternion, explodedQuaternion, e)
scale = restScale
~~~

Проверь, что end больше start. Для намеренно неподвижных деталей задай явную обработку без деления на ноль.

Используй quaternion-интерполяцию для обычных ориентаций. Многократное выкручивание винта, если оно нужно, задавай отдельной абсолютной функцией угла; slerp между двумя ориентациями не описывает несколько полных оборотов.

Не используй накопительные операции вида «на каждом кадре прибавить смещение» для разборки. Они приводят к дрейфу и несовпадению обратной сборки.

При progress = 0 восстанови исходные трансформации точно. При progress = 1 устанавливай конечные трансформации без остаточного недолёта.

### 11.4. Обратимость и детерминированность

Одна и та же деталь при одном и том же progress должна иметь одну и ту же позу независимо от предыдущих действий.

Проверь переходы:

~~~text
0 → 1 → 0
0 → 0.5 → 0.2 → 0.9 → 0
1 → 0.01 → 0.99 → 0
0 → 1 → 0 → 1 → 0
~~~

После повторений не должно появляться накопленного смещения, изменения масштаба, внезапных поворотов или потерянных деталей.

### 11.5. Последовательность разборки

Построй не хаотичный взрыв, а управляемое раскрытие конструкции.

Пример временных диапазонов:

| Прогресс | Основное событие |
| --- | --- |
| 0–20% | Отделяются ободок и задняя крышка |
| 8–30% | Стекло выходит отдельным передним слоем |
| 18–44% | Стрелки отходят от циферблата |
| 26–52% | Отделяются циферблат и его опора |
| 40–70% | Поднимаются мосты, открывая механизм |
| 52–90% | Разводятся колёсные узлы и баланс |
| 58–92% | Отходит заводной барабан |
| 70–100% | Окончательно расходятся крепления и малые детали |

Эти диапазоны — стартовая композиционная схема. Скорректируй их по реальным размерам и пересечениям.

Основная платина остаётся визуальным якорем. Передние слои преимущественно идут вперёд, задняя крышка — назад, внутренние узлы получают умеренные боковые смещения.

Не располагай всё на одной прямой, где крупный циферблат полностью перекрывает механизм. Дай зрителю увидеть внутренние детали под выбранным углом.

Не разбрасывай мелкие винты на огромные расстояния. Между слоями должна сохраняться понятная связь сборки.

### 11.6. Траектории

Простые детали могут двигаться по прямой. Для мест, где прямая проходит сквозь соседнюю геометрию, используй детерминированную кривую или несколько контрольных точек.

Не подключай физический движок только ради этой анимации. Здесь важнее точная повторяемость и красивая управляемая геометрия.

Проверь промежуточные положения, а не только начало и конец. Устрани явные проходы деталей друг сквозь друга, z-fighting и скачки видимости.

## 12. Камера, свет и композиция

### 12.1. Камера

Используй перспективную камеру с умеренным углом обзора. Начальный вид — три четверти: читаются циферблат, толщина корпуса и будущая глубина разборки.

Полностью фронтальный вид может скрывать объём и взаимное расположение деталей. Слишком боковой вид делает циферблат нечитаемым.

Настрой композицию так, чтобы:

- собранные часы были достаточно крупными;
- в разобранном состоянии все основные слои оставались в видимой области;
- подписи и управляющая панель не перекрывали важные детали;
- заводная головка и дужка не обрезались;
- пользовательское вращение не приводило к очевидно сломанному кадру.

Кадрируй сцену с учётом доступной области canvas, а не всей ширины окна. Проверяй границы разборки на нескольких значениях progress.

Для мобильной сцены можно использовать отдельный профиль расстояний между деталями. Это должен быть предсказуемый адаптивный вариант, а не обрезка desktop-композиции.

### 12.2. Управление

Разреши вращение модели мышью и пальцем. Ограничь крайние положения камеры и масштаб так, чтобы пользователь не терял часы.

Панорамирование лучше отключить, если оно не нужно для исследования. Умеренное приближение допустимо.

Действие «Сбросить вид» восстанавливает камеру и target, сохраняя текущую степень разборки. Сборка часов управляется отдельным действием «Собрать».

Перемещение ползунка не должно сбрасывать пользовательский ракурс.

Не включай постоянное автоматическое вращение по умолчанию. Если добавишь такой режим, сделай его явным и управляемым.

### 12.3. Освещение

Используй студийный свет:

- мягкий основной источник;
- слабое заполняющее освещение;
- контровой или боковой источник для силуэта;
- контролируемые отражения металла.

Предпочти локальный environment-ресурс или программно построенное окружение. Не привязывай первый запуск к внешнему HDRI-пресету без резервного варианта.

Если применяешь тень, проверь её при разборке: неподвижная запечённая тень не должна оставаться силуэтом собранных часов под разлетевшимися деталями.

Не делай сильный bloom, тяжёлую глубину резкости и размытие по всему экрану. Детали механизма должны оставаться различимыми.

## 13. Выбор деталей и подписи

Пользователь должен иметь возможность узнать, что он видит.

Добавь выбор основных деталей:

- клик по видимой части модели;
- касание на телефоне;
- доступный список узлов в обычном DOM для клавиатуры.

Отличай клик от перетаскивания камеры по порогу движения указателя. Поворот модели не должен случайно выбирать детали.

Выделение делай сдержанным: изменение материала, тонкий контур или небольшой световой акцент. Не превращай деталь в непрозрачное яркое пятно.

В режиме подписей:

- привязывай подпись к нужному узлу;
- учитывай видимость и перекрытие;
- не показывай подписи скрытых внутренних деталей поверх закрытого корпуса;
- ограничь количество одновременно видимых подписей;
- исключай перекрытие с ползунком и панелью информации;
- на телефоне показывай прежде всего подпись выбранного узла.

Не используй hover как единственный способ получить информацию. Для выбранной детали должны работать обычные кнопки, фокус и действие закрытия.

Не создавай десятки мелких обязательных Tab-остановок на декоративных 3D-метках. Клавиатурный доступ обеспечь понятным списком основных узлов.

## 14. Поведение кнопок и программной анимации

«Разобрать» переводит progress из текущего значения к 1. «Собрать» переводит его из текущего значения к 0.

Движение плавное, с умеренной длительностью: ориентировочно 8–10 секунд на полный проход. Для неполного пути длительность пропорционально сокращается.

Во время такого перехода:

- видимый ползунок и процент синхронизируются с моделью;
- доступна пауза;
- ручное изменение ползунка останавливает программный переход;
- повторная команда не создаёт второй параллельный цикл;
- после завершения устанавливается точное конечное значение.

При скрытии вкладки приостанови необязательное движение. Не допускай огромного скачка из-за накопленного delta после возвращения.

Не запускай разборку автоматически при открытии сайта. Пользователь должен сначала увидеть собранные часы и понять управление.

Если поддерживается prefers-reduced-motion, отключи декоративное движение и длинные программные переходы: кнопки могут сразу устанавливать нужную конфигурацию. Ручной ползунок продолжает работать напрямую.

### 15.3. Состояние и обновление кадров

Сделай один источник истины для progress. Удобно хранить актуальное числовое значение в контроллере или ref, а DOM-представление синхронизировать по событиям и с разумной частотой.

React state на событии пользовательского input допустим. Не выполняй тяжёлый React-render всей сцены на каждом кадре ради изменения положения деталей.

В кадровом цикле:

- считывай progress;
- вычисляй абсолютные трансформации;
- обновляй ссылки на нужные Object3D;
- не создавай новые геометрии и материалы;
- не выделяй без необходимости новые векторы и quaternion-объекты;
- не делай повторный обход всей сцены для поиска имён.

Найди узлы один раз при загрузке, проверь соответствие манифесту и сохрани ссылки.

Если используешь рендеринг по требованию, явно запрашивай кадр после изменения progress и во время активного программного движения или работы controls. Не допускай ситуации, когда slider обновился, а canvas остался на старом кадре.

При завершении движения прекращай ненужный постоянный рендер, если сцена больше не меняется.

### 15.4. Загрузка

При загрузке показывай понятный статус «Загружаем 3D-модель».

Показывай числовой процент только при наличии достоверного измерения. Не анимируй выдуманные 0–100%, не связанные с загрузкой.

После загрузки проверь наличие обязательных узлов. Если в модели нет нескольких ключевых деталей, выдай диагностируемую ошибку и исправь модель или манифест.

Подключи error boundary или эквивалентный механизм. У посетителя не должен оставаться бесконечный пустой canvas при сбое.

### 15.5. Резервная геометрия

Если импорт подходящей модели недоступен, создай настоящую процедурную модель с отдельными деталями. Она должна иметь корпус, циферблат, стрелки, стекло, крышку и осмысленный внутренний механизм.

Не загружай случайный GLB по непроверенной внешней ссылке. Не используй модель одним неразделённым мешем в надежде имитировать разборку CSS-трансформацией.

Резервная модель — это рабочая 3D-геометрия. Она не должна быть просто стопкой дисков, если её внешний вид перестал напоминать часы.

## 16. Производительность и ресурсы

Поддержи разумную плавность на обычном ноутбуке и современном телефоне.

Стартовые бюджеты:

| Параметр | Ориентир |
| --- | --- |
| Размер основного GLB | Желательно до 15 МБ |
| Геометрия desktop | Примерно 50–120 тысяч треугольников |
| Мобильная геометрия | По возможности до 60 тысяч треугольников |
| Draw calls | Желательно до 100, с сокращением на телефоне |
| Текстуры | Обычно 1K; 2K только для видимой пользы |
| Pixel ratio desktop | Ограниченный, обычно не выше 1.5–1.75 |
| Pixel ratio mobile | Подбираемый, обычно около 1–1.25 |
| Отклик ползунка | Без заметной задержки |

Это ориентиры для оптимизации, а не гарантии частоты кадров на любом устройстве.

Не ухудшай модель слепо ради формального числа. Сначала измерь нагрузку и найди реальные причины.

Для повторяющихся креплений используй общие геометрии и материалы. Инстансинг допустим, если сохраняется индивидуальная управляемость нужных деталей.

Meshopt, Draco и другие способы сжатия применяй только вместе с проверенной доставкой нужных декодеров. Первый запуск не должен ломаться из-за отсутствующего WASM или внешнего CDN.

Постобработка, сложное стекло и динамические тени должны иметь облегчённый режим. При снижении качества сохраняй читаемость механизма и рабочую разборку.

Не перезагружай модель при движении ползунка. Не пересоздавай Canvas при изменении выбранной детали.

Освобождай принадлежащие сцене ресурсы при размонтировании и корректно управляй общими кешированными материалами.

Проверь production-сборку, а не только dev-сервер.

## 17. Адаптивность

Проверь как минимум:

- 360 × 800;
- 390 × 844;
- 768 × 1024;
- 1280 × 800;
- 1440 × 900;
- широкое desktop-окно.

На телефоне:

- ползунок остаётся полностью доступным;
- элементы управления имеют удобную область касания;
- модель не уходит за границы при 100%;
- подписи не перекрывают весь экран;
- пояснения можно читать без горизонтального скролла;
- панель не закрывает нижнюю часть сцены;
- учитываются safe-area-inset и динамическая высота viewport;
- контент может нормально прокручиваться, если он не помещается.

Не фиксируй весь интерфейс в высоту 100vh, если это обрезает управление на маленьком экране. Используй подходящие viewport-единицы с нормальным поведением содержимого.

Раздели жесты по зонам: внутри сцены — управление моделью, на ползунке — изменение прогресса, вне сцены — обычная прокрутка страницы. Не ставь глобальный запрет прокрутки на весь документ.

При смене ориентации и размера окна пересчитывай кадрирование, сохраняя progress.

## 18. Доступность

Используй нативный input type="range" как основу ползунка.

Обеспечь:

- связанный label «Разборка часов»;
- корректные min, max, step и value;
- понятный aria-valuetext, например «Разобрано на 47 процентов»;
- видимый фокус;
- управление стрелками, Home и End;
- достаточную область касания, ориентировочно 44 × 44 px для основных действий;
- логичный порядок Tab;
- доступные названия и состояния переключателей.

Не дублируй нативную семантику range лишними конфликтующими ролями. Если добавляешь Page Up / Page Down, реализуй их последовательно и без двойной обработки встроенных клавиш.

Процент и подписи должны быть обычным HTML-текстом, а не только пикселями внутри canvas.

Обновления статуса для screen reader не должны озвучиваться каждый кадр. Сообщай о смене крупного этапа или конечном результате с умеренной частотой.

Добавь текстовое описание сцены и доступный список основных узлов. Пользователь клавиатуры должен иметь возможность исследовать функции деталей без точного попадания в 3D-меш.

Учитывай prefers-reduced-motion. При увеличении масштаба страницы до 200% управление и пояснения остаются доступными.

Не включай звук автоматически. Звуковая имитация тиканья не требуется для выполнения задания.

## 19. Ошибки и граничные случаи

Обработай следующие ситуации:

| Ситуация | Ожидаемое поведение |
| --- | --- |
| GLB не загрузился | Понятное сообщение и работающая повторная попытка |
| WebGL недоступен | Изображение часов и текст о необходимости поддержки 3D |
| Потерян WebGL-контекст | Контролируемое восстановление или повторная инициализация |
| Быстрое движение ползунка | Сцена следует последнему значению, очереди анимаций не накапливаются |
| Ручной ввод во время автоперехода | Автопереход останавливается |
| Кнопка нажата в конечном состоянии | Стабильное поведение без скачка |
| Изменение размера окна | Прогресс сохраняется, кадрирование обновляется |
| Переключение подписи | Прогресс и ракурс сохраняются |
| Сброс вида | Сбрасывается камера, а не разборка |
| Выбранная деталь скрылась | Панель остаётся понятной, 3D-метка не рисуется сквозь всё |
| Возврат во вкладку | Нет неконтролируемого скачка движения |
| Низкая производительность | Снижается качество эффектов, основной функционал сохраняется |

Fallback-изображение допустимо при ошибке или отсутствии WebGL. В нормальном режиме оно не заменяет 3D-модель.

При отсутствии 3D отключи недействующие элементы разборки и объясни состояние. Не оставляй активный ползунок, который ничего не меняет.

Не добавляй кнопки повторной попытки, которые фактически не инициируют новую загрузку.

## 20. Критерии визуального качества

Перед завершением внимательно оцени:

1. С первого взгляда понятно, что это карманные часы.
2. В собранном виде совпадают стекло, ободок, циферблат и корпус.
3. Стрелки находятся над циферблатом, а не проваливаются в него.
4. Металл читается как металл, эмаль — как эмаль, стекло — как стекло.
5. Внутренний механизм содержит узнаваемые узлы, а не случайные формы.
6. На 50% уже видна польза разборки.
7. На 100% можно проследить связь слоёв и место каждой основной детали.
8. Мелкие элементы не исчезают на фоне.
9. Свет не засвечивает циферблат и не скрывает зубья колёс.
10. Заголовок не конкурирует с объектом по площади.
11. Ползунок визуально связан со сценой.
12. На телефоне композиция остаётся собранной и понятной.

Сделай визуальную проверку скриншотами, исправь найденные проблемы и повтори только затронутые проверки.

## 21. Проверки поведения

### 21.1. Чистая функция трансформаций

Отдели расчёт позы детали от рендера настолько, чтобы проверить ключевые свойства:

- progress = 0 возвращает исходную трансформацию;
- progress = 1 возвращает конечную трансформацию;
- значения до начала и после конца диапазона корректно ограничиваются;
- одинаковый progress даёт одинаковую позу;
- многократный проход туда и обратно не создаёт дрейфа;
- quaternion нормализован;
- данные не содержат NaN и бесконечностей.

Пиши содержательные тесты для этой механики, если в проекте есть тестовая инфраструктура или её разумно добавить. Не создавай десятки тестов, которые лишь повторяют структуру JSX.

### 21.2. Ручная браузерная проверка

Обязательно проверь:

1. Первый запуск и загрузку ресурсов.
2. Собранное состояние.
3. Промежуточные состояния 25%, 50% и 75%.
4. Полную разборку.
5. Полную обратную сборку.
6. Быстрое перемещение ползунка в обе стороны.
7. Сборку и разборку кнопками.
8. Паузу и ручное прерывание программной анимации.
9. Вращение модели на разных стадиях.
10. Сброс камеры без изменения progress.
11. Выбор и снятие выделения детали.
12. Подписи на desktop и mobile.
13. Управление ползунком с клавиатуры.
14. Уменьшенное движение.
15. Ошибку загрузки модели и повторную попытку.
16. Fallback при недоступном WebGL, насколько это проверяемо в среде.

## 27. Работа через Blender MCP и восстановление соединения

### 27.1. Один понятный маршрут управления

Используй одну рабочую связку клиента, MCP-сервера и выбранного экземпляра Blender.

Если открыто несколько экземпляров Blender, явно определи, какой обслуживает этот проект. Тестовый объект должен появляться именно в нужной сцене.

Не отправляй сотни зависимых команд параллельно в одну сцену. Операции, меняющие общие объекты, материалы, выделение и активный контекст Blender, выполняй последовательно.

Объединяй однотипную работу в небольшие воспроизводимые Python-операции: например, создание набора креплений или назначение материалов. После каждого крупного этапа проверяй сцену.

### 27.2. Не путай каналы связи

Различай:

1. Запуск MCP-процесса клиентом.
2. Доступность MCP-инструментов.
3. Соединение MCP-процесса с аддоном Blender.
4. Выполнение команды в нужной сцене.
5. Запись и чтение экспортированного файла.

Успех предыдущего пункта не доказывает успех следующего.

Если перечисление инструментов работает, но команда в сцене завершается ошибкой, исследуй соединение с Blender. Если объект создан, но GLB не появляется, проверяй путь, экспорт и файловую доступность.

### 27.3. Перезапуск без потери работы

Перед необходимым перезапуском клиента или Blender:

- сохрани .blend и исходники;
- запиши текущий этап и оставшиеся действия;
- сохрани обезличенную диагностику;
- проверь отсутствие несохранённой чужой работы;
- используй доступный штатный механизм перезапуска.

Если перезапуск AI-клиента технически завершает текущую сессию и агент не может выполнить его с автоматическим продолжением, не обещай сделать это незаметно. Сохрани всё подготовленное и продолжай доступные части проекта. Не закрывай приложение с несохранённой работой ради формальной отметки об установке.

### 27.4. Диагностика по причине

При ошибке не повторяй одну команду бесконечно. Раздели причины:

- исполняемый файл не найден;
- несовместимая версия;
- неверный путь;
- занятый порт;
- Blender не запущен;
- аддон не включён;
- разные адреса или порты;
- сервер ещё не обнаружен клиентом;
- ошибка Python внутри сцены;
- отсутствие права записи в выбранную папку.

Исправь установленную причину и повтори соответствующую проверку. Не переустанавливай все компоненты после любой ошибки.

## 28. Параметрическая спецификация модели

### 28.1. Размеры и пропорции

Для согласованной авторской модели возьми диаметр корпуса D за базовую величину.

Начальные пропорции:

| Элемент | Ориентир относительно D |
| --- | --- |
| Внешний диаметр корпуса | 1.00 D |
| Толщина основного корпуса | 0.18–0.24 D |
| Видимый диаметр циферблата | 0.82–0.88 D |
| Толщина переднего ободка | 0.025–0.045 D |
| Диаметр заводной головки | 0.11–0.15 D |
| Наружная высота дужки | 0.17–0.23 D |
| Длина часовой стрелки от оси | 0.22–0.27 D |
| Длина минутной стрелки от оси | 0.32–0.37 D |

Это художественные ориентиры, а не спецификация исторической модели. Согласуй их между собой, проверь силуэт и скорректируй при необходимости.

Используй единый набор параметров при генерации деталей. Изменение D не должно разрывать посадочные места и приводить к несоразмерным винтам.

### 28.2. Корпус и крышки

Построй корпус с осмысленным профилем: наружный борт, внутренний посадочный пояс, небольшие фаски и отдельные передний и задний элементы.

Для круглых деталей можно использовать вращение профиля. Не делай каждую металлическую поверхность плоским цилиндром с острыми краями.

Фаски должны поддерживать блик и масштаб. Крупная фаска, съедающая весь тонкий ободок, выглядит как игрушечная деталь.

Не добавляй переднюю откидную крышку: выбранный тип часов имеет открытый циферблат. Задняя крышка в демонстрации отделяется вдоль оси, без ненужной сложной кинематики петель.

### 28.3. Циферблат и стрелки

Выбери один стиль меток, например римские цифры, и выдержи его на всём циферблате. Предусмотри крупные часовые деления и более тонкие минутные.

Не превращай каждое деление в отдельный тяжёлый объект, если достаточно общей геометрии или качественной текстуры.

Для цифр используй доступный шрифт с понятным происхождением. Проверь читаемость, центровку и отсутствие зеркального отображения после экспорта.

Настрой декоративное положение стрелок около 10:10. Реальное текущее время и непрерывный ход не обязательны.

Две основные стрелки располагаются на общей оси, но имеют собственные pivot и небольшое разделение по глубине. Они не должны пересекать стекло в собранном состоянии.

### 28.4. Зубчатые колёса

Построй несколько колёс разных размеров:

- различимый обод;
- настоящий зубчатый внешний контур;
- центральное отверстие или ступицу;
- несколько спиц там, где они видимы;
- разницу материалов или обработки у отдельных узлов.

Для демонстрационного зубчатого контура допустимо параметрическое чередование радиусов с аккуратными боковыми гранями. Эвольвентный профиль нужен только при заявленной инженерной точности.

Число зубьев должно быть целым и согласованным с размером колеса. Не копируй один и тот же рисунок на все размеры.

Если показываешь вращение сцепленных колёс в отдельном явно включённом режиме, согласуй направления и относительные скорости. Если это не реализовано убедительно, оставь колёса неподвижными относительно собственного узла.

### 28.5. Мелкие детали

Сделай винты узнаваемыми по шляпке и пазу. У втулок и осей должны быть понятные посадочные места.

Баланс можно построить как тонкое колесо с мостом и небольшими опорами. Пружину показывай только при достаточном качестве и бюджете геометрии.

Не моделируй тысячи витков, невидимых после экспорта. Сосредоточь детализацию в тех местах, которые пользователь действительно увидит в exploded-view.

### 28.6. Повторяемая генерация

Разбей Blender-скрипт на понятные операции:

~~~text
prepare_project_collection
create_materials
build_case
build_dial
build_hands
build_movement
build_crown_and_bow
build_fasteners
create_animation_carriers
validate_assembly

~~~

Это предлагаемые имена твоих функций, а не готовые команды Blender API. Реализуй их с учётом фактической версии Blender.

Генерация должна быть воспроизводимой. Если применяешь случайную микрофактуру, используй фиксированный seed.

## 29. Пространственная композиция разборки

### 29.1. Направления и дистанции

Ниже — исходная схема смещений для художественной настройки. Смещения выражены относительно исходной позиции детали в согласованном пространстве анимации.

| Группа | Основное направление | Начальный ориентир дистанции |
| --- | --- | --- |
| Передний ободок | +Z | 0.70–0.95 D |
| Стекло | +Z | 0.55–0.75 D |
| Стрелки | +Z с небольшим боковым разведением | 0.38–0.58 D |
| Циферблат | +Z | 0.25–0.40 D |
| Опора циферблата | +Z | 0.12–0.22 D |
| Основная платина | Почти неподвижна | 0–0.05 D |

| Колёсные узлы | Небольшие разные XY-смещения и глубина | 0.12–0.30 D |

| Головка и вал | Вверх вдоль направления завода | 0.08–0.16 D |

Не копируй числа без просмотра сцены. Это стартовые значения, которые нужно адаптировать к геометрии, ракурсу и размеру экрана.

Большинство крупных слоёв сохраняет почти исходную ориентацию. Случайные повороты на 90–180 градусов ухудшают понимание устройства.

### 29.2. Крепления и вложенные узлы

Определи, с какой деталью движется каждый винт до собственного отделения.

Если винт установлен на мосту, допустима структура:

~~~text
bridge_carrier
  bridge_mesh
  screw_carrier
    screw_mesh
~~~

Тогда bridge_carrier переносит всю сборку, а screw_carrier получает только дополнительное локальное смещение на своём этапе. Не добавляй смещение моста повторно к винту.

Если используешь плоскую иерархию, вычисляй следование узлу явно и детерминированно. Не смешивай обе схемы для одной детали.

При необходимости добавь в манифест parentId или иной однозначный признак пространства. Укажи в MODEL.md, как интерпретируются исходные и конечные трансформации.

### 29.3. Просмотр траекторий

Для проверки сделай режим разработчика, который по необходимости:

- показывает оси и bounding boxes;
- отмечает центры узлов;
- выводит выбранное имя детали;
- позволяет быстро установить контрольный progress;
- показывает траекторию проблемной детали.

В обычном интерфейсе посетителя этот режим выключен. Технические имена, координаты и диагностические показатели не должны занимать основной экран.

Проверь траектории хотя бы на 11 равномерных значениях от 0 до 1 и дополнительно в местах начала и окончания стадий. Это полезнее, чем оценивать только красивый последний кадр.

## 30. Эталон функций прогресса и позы

Ниже — ориентир для архитектуры. Его можно адаптировать, сохранив абсолютный расчёт, нормализацию и отсутствие дрейфа.

~~~ts
type Vec3Tuple = [number, number, number];

type LinearPartMotion = {
  start: number;
  end: number;
  restPosition: Vec3Tuple;
  explodedOffset: Vec3Tuple;
};

export function clamp01(value: number): number {
  if (!Number.isFinite(value)) {
    throw new Error("Progress must be a finite number");
  }

  return Math.min(1, Math.max(0, value));
}

export function validateMotionRange(start: number, end: number): void {
  if (
    !Number.isFinite(start) ||
    !Number.isFinite(end) ||
    start < 0 ||
    end > 1 ||
    end <= start
  ) {
    throw new Error("Part motion requires 0 <= start < end <= 1");
  }
}

export function phase(
  progress: number,
  start: number,
  end: number,
): number {
  validateMotionRange(start, end);
  return clamp01((clamp01(progress) - start) / (end - start));
}

export function smoothstep01(value: number): number {
  const t = clamp01(value);
  return t * t * (3 - 2 * t);
}

export function evaluatePosition(
  motion: LinearPartMotion,
  progress: number,
  output: Vec3Tuple,
): Vec3Tuple {
  const amount = smoothstep01(phase(progress, motion.start, motion.end));

  output[0] = motion.restPosition[0] + motion.explodedOffset[0] * amount;
  output[1] = motion.restPosition[1] + motion.explodedOffset[1] * amount;
  output[2] = motion.restPosition[2] + motion.explodedOffset[2] * amount;

  return output;
}

export function transitionDurationMs(
  from: number,
  to: number,
  fullDurationMs = 9000,
): number {
  if (!Number.isFinite(fullDurationMs) || fullDurationMs <= 0) {
    throw new Error("Full transition duration must be positive");
  }

  return Math.abs(clamp01(to) - clamp01(from)) * fullDurationMs;
}
~~~

В реальном кадровом цикле заранее выделяй output и переиспользуй его. Полную проверку манифеста выполни при загрузке, чтобы не валидировать одни и те же неизменные данные заново для каждой детали на каждом кадре.

Неподвижные детали не обязаны иметь искусственный диапазон с нулевым смещением. Их можно исключить из массива анимируемых узлов.

Для quaternion-позы используй соответствующую интерполяцию с тем же amount, не меняя исходные quaternion-значения.

### 30.1. Программный переход

При запуске запомни:

~~~text
from = текущее значение progress
to = 0 или 1
duration = fullDuration × abs(to − from)
elapsed = 0
~~~

Пока переход активен, увеличивай elapsed только на допустимое активное время:

~~~text
t = clamp(elapsed / duration, 0, 1)
progress = from + (to − from) × t
~~~

Если duration равно нулю, сразу установи конечное значение и не запускай цикл.

Линейный ход progress удобен для ползунка; плавность движения отдельных деталей уже задаётся их локальной функцией. Если вводишь дополнительное easing для общего перехода, проверь, что суммарный результат не зависает визуально возле краёв.

При скрытии вкладки приостанови отсчёт. При возобновлении не прибавляй всё прошедшее фоновое время одним кадром.

### 30.2. Владение управлением

Ручной ввод и программный переход используют один progressController.

Рекомендуемый набор операций:

~~~text
setProgressFromUser(value)
animateTo(value)
pause()
getProgress()
subscribeToUiUpdates(listener)
~~~

При setProgressFromUser:

1. Прерви текущий программный переход.
2. Ограничь входное значение диапазоном.
3. Сохрани progress.
4. Обнови DOM-представление.
5. Запроси кадр сцены, если используется рендеринг по требованию.

Не поддерживай два независимо изменяемых значения «процент слайдера» и «процент 3D-модели».

## 31. Конкретный контракт состояний интерфейса

### 31.1. Основные состояния

Предусмотри минимальные различимые состояния:

~~~text
loading
ready
animating
paused
load-error
webgl-unavailable
~~~

Не обязательно хранить их одним enum, если надёжнее разделить загрузку ресурсов и транспорт анимации. Смысл в непротиворечивом поведении.

| Состояние | Ползунок | Основное действие | Дополнительное поведение |
| --- | --- | --- | --- |
| Загрузка | Недоступен | Статус загрузки | Нет ложного рабочего canvas |
| Готово | Доступен | Собрать / разобрать | Доступны ракурс и выбор деталей |
| Программное движение | Доступен | Пауза | Ручной input прерывает движение |
| Пауза | Доступен | Продолжить или выбрать направление | Текущее положение сохраняется |
| Ошибка модели | Недоступен | Повторить загрузку | Понятное описание ошибки |
| Нет WebGL | Недоступен | Информация о режиме | Доступны изображение и пояснение |

Если реализуешь «Продолжить», сохраняй цель приостановленного перехода. Если выбираешь более простой вариант, кнопки «Собрать» и «Разобрать» запускают движение из текущего положения.

### 31.2. Процент и этап

Используй одну функцию форматирования процента. Для обычного текстового индикатора достаточно целого значения; фактический шаг slider может быть более мелким.

При округлении промежуточное значение не должно объявляться завершённой сборкой. Состояния «Собраны» и «Разобраны» определяй по реальному progress с явно выбранным допуском, а не только по округлённому тексту.

Подпись этапа может принимать значения:

- «Собраны»;
- «Раскрывается корпус»;
- «Открывается циферблат»;
- «Раскрывается механизм»;
- «Разобраны».

Процент и этап помогают пользователю, но не заменяют плавную модель.

### 31.3. Отсутствие неожиданных сбросов

Переключение подписи, выбор детали, открытие пояснения и изменение размера окна сохраняют progress.

Выбор детали не запускает автоматическую разборку без явного действия пользователя. Если нужен переход к стадии, где деталь видима, предложи понятную кнопку вроде «Показать в разборке».

Не добавляй скрытые глобальные горячие клавиши, перехватывающие обычную прокрутку или ввод в ползунке.

## 32. Детали реализации 3D-сцены

### 32.1. Кеш и экземпляры модели

Если загрузчик кеширует GLB, не изменяй общий экземпляр сцены так, чтобы повторное открытие страницы начиналось с предыдущей разборки.

Используй корректно подготовленный экземпляр для этой сцены и сохраняй rest-transform до первой анимации. При повторной инициализации исходные данные должны оставаться исходными.

Выделение детали не должно изменять общий материал всех остальных объектов с тем же material reference. Для временного выделения используй отдельную стратегию или управляемую копию материала.

Убери обработчики и подписки при размонтировании. Проверь повторную инициализацию в режиме разработки, если среда её выполняет.

### 32.2. Обновление матриц

Если используешь вычисления world position, bounding box, raycasting или экранных подписей сразу после изменения позы, учитывай актуальность матриц объектов.

Не считывай старые мировые координаты и не исправляй запаздывающую подпись случайной задержкой в несколько кадров.

### 32.3. Стекло и выбор деталей

Стекло не должно делать циферблат серым непрозрачным диском.

Подбери толщину, отражения, прозрачность и порядок рендера. Проверь отображение при взгляде с разных сторон.

Определи правила выбора: большой прозрачный слой не должен перехватывать каждый клик по видимой детали под ним. Например, обычный клик может выбирать значимую непрозрачную деталь, а стекло доступно через список узлов.

Не меняй глобально raycasting всех объектов ради одного проблемного слоя.

### 32.4. Ресурсы и цвета

Разделяй цветовые текстуры и карты данных при настройке color space. Нормали и roughness не должны интерпретироваться как обычные цветные изображения.

Проверь единый результат тонального преобразования и экспозиции. Если циферблат выглядит серым, исправляй свет и материал осознанно, а не делай весь объект самосветящимся.

Следуй рекомендациям [React Three Fiber о производительности](https://r3f.docs.pmnd.rs/advanced/pitfalls): переиспользуй ресурсы, обновляй быстрые трансформации вне тяжёлого React-render и избегай ненужного пересоздания сцены.

## 33. Проверки экспорта, данных и пользовательского сценария

### 33.1. Проверка до запуска сайта

Добавь небольшую содержательную проверку итогового GLB и манифеста выбранными доступными средствами.

Проверь:

- GLB существует и имеет ненулевой размер;
- файл корректно разбирается;
- обязательные имена узлов присутствуют;
- id и nodeName анимируемых деталей уникальны;
- ссылки на родителей корректны и не образуют цикл;
- координаты и масштабы конечны;
- quaternion имеет допустимую длину и нормализуется;
- диапазоны удовлетворяют 0 ≤ start < end ≤ 1;
- все управляемые объекты находятся в ожидаемой иерархии;
- внешние ресурсы, если они есть, действительно доступны;
- манифест соответствует этой версии модели.

Не создавай «успешный» отчёт, который проверяет лишь наличие файла с нужным расширением.

Если используются компрессия и расширения glTF, проверь их поддержку загрузчиком.

### 33.2. Разделение ошибок

Различай ошибки конфигурации модели и пользовательский сбой сети.

Отсутствующий nodeName в поставляемом тобой GLB — это ошибка проекта, которую нужно исправить до передачи. Кнопка повторной загрузки её не решает.

Сетевая ошибка при временной недоступности ресурса может иметь повторную попытку. Для повторной попытки очисти нужное состояние ошибки и действительно запусти загрузку заново.

### 33.3. Автоматизация поведения

Если в среде есть подходящие инструменты браузерной автоматизации, проверь ими ключевой маршрут:

~~~text
открыть страницу
    → дождаться готовности 3D
        → установить 0%
            → установить 50%
                → установить 100%
                    → вернуть 0%
                        → проверить сохранение исходной позы
~~~

Для такой проверки можно предоставить диагностическое чтение progress и числа привязанных деталей в режиме теста. Оно не должно подменять реальное движение canvas.

Обычный screenshot интерфейса с надписью «100%» ещё не доказывает, что детали изменили трансформации. Проверяй оба уровня.

Сравнивай позиции с разумным численным допуском, а ориентации — с учётом того, что quaternion q и −q обозначают один поворот.

Не обещай автоматическую проверку всех физических пересечений только на основании bounding boxes. Грубые границы помогают найти кандидатов, а визуальная оценка сложных форм остаётся необходимой.
